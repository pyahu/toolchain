# Maintainers

## Current ownership

| Maintainer | Role | Areas |
| ---------- | ---- | ----- |
| [Terson Rigaud (@trigaud)](https://github.com/trigaud) | Lead maintainer | Catalog policy, releases, security response, governance, final review |

The lead maintainer is the code owner for the repository. Maintainer status reflects active service,
not permanent ownership; future maintainers can be added by a documented pull request approved by
an existing maintainer.

## Expected response times

These are service targets, not guarantees:

- security reports: acknowledgement within three business days and initial assessment within seven;
- bug reports and tool proposals: first triage within seven calendar days;
- ready pull requests: first review within ten business days;
- release-blocking regressions: status update within two business days.

If a target is missed, a polite follow-up on the original thread is welcome. Lack of response does
not imply acceptance of a proposal. The project may close requests that lack the requested
reproduction, rationale, or follow-up after giving the contributor a reasonable opportunity to
respond.

## Decision process

Routine changes use the contribution criteria and automated gates. Material changes to the base
profile, supported platforms, certification contract, or update channel require an issue explaining
the user impact before implementation. The lead maintainer resolves deadlocks and records the
rationale in the issue or pull request.

Security matters follow [SECURITY.md](SECURITY.md); community conduct follows
[CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md).
